## 1. Scope and evidence

The uploaded archive contains one 32 KiB `.sms` image. The ROM identity matches the public catalog entry for Charles MacDonald's Scroll Test Program, version 1.00, dated 2001-07-30. The SMS Power release page says its original downloadable archive includes source, but the user-provided archive contains only the ROM image.

This audit distinguishes:
- facts derived from the ROM bytes and static Z80 control-flow inspection;
- source-level comparisons against Ares and MAME;
- behavior that still requires actual execution and frame comparison.

No claim is made that the ROM has been executed in this emulator, Ares, or MAME during this investigation.

## 2. The ROM is not a hardware-sprite movement test

The ROM programs R5 as `$FF`, placing the Mode 4 SAT at `$3F00`. Its initialization writes the SMS sprite-Y terminator `$D0` to the first 64 SAT bytes. The program then loads graphics data into VRAM and updates VDP scroll registers R8 and R9. Static inspection finds no subsequent SAT animation/update path.

Therefore, the moving visual in this ROM is generated by the Mode 4 background/name-table scroll, not by moving a hardware sprite through SAT X/Y attributes. It may visually resemble an overlaid object, but it is not evidence of SAT sprite motion.

## 3. Z80 program flow

### 3.1 Interrupt vector

At `$0038`, the ROM reads VDP status from port `$BF`, calls the handler at `$0068`, enables interrupts, and returns with `RETI`.

The handler at `$0068`:
1. increments RAM byte `$C002`;
2. writes that value to VDP register R9 (vertical scroll);
3. decrements RAM byte `$C003`;
4. writes that value to VDP register R8 (horizontal scroll).

The interrupt handler therefore changes both scroll registers once per serviced interrupt. R1 is later programmed to `$E2`, enabling display and VINT; R10 is initialized to `$FF`, so the visible behavior should be treated primarily as a VINT-driven update, not a per-scanline HINT animation.

### 3.2 Main loop

The main loop polls V Counter through port `$7E`:
- when VCounter reaches `$40`, it increments `$C000` and writes the value to R8 and R9;
- when VCounter reaches `$80`, it decrements `$C001` and writes the value to R8 and R9;
- it then repeats.

This creates writes to R8/R9 during the active display at two distinct vertical positions, in addition to the interrupt-driven updates. It is therefore a useful diagnostic for the different application/latch behavior of horizontal and vertical scroll, not just a static horizontal offset.

## 4. Comparison with emulator implementations

### 4.1 MAME — Sega 315-5124

Source: [MAME 315_5124.cpp](https://github.com/mamedev/mame/blob/master/src/devices/video/315_5124.cpp)

The current MAME source:
- copies R8 at the line timer;
- allows a write to update the R8 copy only through the configured X-scroll latch boundary (HPos 21 for the 315-5124);
- copies R9 at the beginning of the active display;
- computes the fine-scroll leading-pixel palette selector from `tile_line - 1`, where `tile_line` already includes the low three bits of the active vertical-scroll value.

The last point is the confirmed source-level discrepancy fixed by PR #920.

### 4.2 Ares

Source: [Ares SMS background.cpp](https://raw.githubusercontent.com/ares-emulator/ares/master/ares/ms/vdp/background.cpp)

Ares' `Background::setup()` copies both HScroll and VScroll into its background latch. `graphics3()` then uses those latched values for background coordinate generation. Since setup is part of its scanline pipeline, this is a different R9 update model from MAME's active-display-start capture.

This difference must not be resolved by blindly choosing one emulator. It requires hardware evidence or a test ROM whose expected result is independently established.

### 4.3 Sega Emulator

Source: `native/video_core/src/sms/vdp.rs`

The current model:
- maintains an R8 latch for the following scanline, with the HPos 21 write boundary;
- holds active-display R9 writes as pending and applies them at the completed-visible-frame boundary;
- renders the Mode 4 background using source coordinates derived from R8/R9;
- previously selected the fine-scroll leading-pixel tile-$100 row from `(output_y - 1) & 7`, omitting `R9 & 7`.

The R8/R9 latch model is structurally closer to MAME than to Ares. This is a source-level comparison, not proof of physical hardware accuracy.

## 5. Confirmed renderer discrepancy

MAME derives the tile-$100 selector row from its `tile_line` calculation:

```text
tile_line = output_y - (8 - (R9 & 7))
parse_line = tile_line - 1
parse_row = (output_y + (R9 & 7) - 1) & 7
```

The previous Sega Emulator code used:

```text
parse_row = (output_y - 1) & 7
```

For nonzero fine vertical scroll, this reads a different bitplane row and can choose the wrong background palette for the first 1–7 pixels of a line when R8 has a nonzero fine-scroll component.

PR #920 updates the row calculation and adds a regression test for R8=3, R9=1. The test distinguishes row 0 from row 7 in tile $100.

This is a localized, reproducible mismatch. It does not by itself explain the entire reported visual failure.
