## 1. Scope and evidence

The uploaded archive contains one 32 KiB `.sms` image. The ROM identity matches the public catalog entry for Charles MacDonald's Scroll Test Program, version 1.00, dated 2001-07-30. The SMS Power release page says its original downloadable archive includes source, but the user-provided archive contains only the ROM image.

This audit distinguishes:

No claim is made that the ROM has been executed in this emulator, Ares, or MAME during this investigation.

## 2. The ROM is not a hardware-sprite movement test

The ROM programs R5 as `$FF`, placing the Mode 4 SAT at `$3F00`. Its initialization writes the SMS sprite-Y terminator `$D0` to the first 64 SAT bytes. The program then loads graphics data into VRAM and updates VDP scroll registers R8 and R9. Static inspection finds no subsequent SAT animation/update path.

Therefore, the moving visual in this ROM is generated by the Mode 4 background/name-table scroll, not by moving a hardware sprite through SAT X/Y attributes. It may visually resemble an overlaid object, but it is not evidence of SAT sprite motion.

## 3. Z80 program flow

### 3.1 Interrupt vector

At `$0038`, the ROM reads VDP status from port `$BF`, calls the handler at `$0068`, enables interrupts, and returns with `RETI`.

The handler at `$0068`:
1. increments RAM byte `$C002`;
2. writes that value to VDP register R9 (vertical scroll);
3. decrements RAM byte `$C003`;
4. writes that value to VDP register R8 (horizontal scroll).

The interrupt handler therefore changes both scroll registers once per serviced interrupt. R1 is later programmed to `$E2`, enabling display and VINT; R10 is initialized to `$FF`, so the visible behavior should be treated primarily as a VINT-driven update, not a per-scanline HINT animation.

### 3.2 Main loop

The main loop polls V Counter through port `$7E`:
- when VCounter reaches `$40`, it increments `$C000` and writes the value to R8 and R9;
- when VCounter reaches `$80`, it decrements `$C001` and writes the value to R8 and R9;
- it then repeats.

This creates writes to R8/R9 during the active display at two distinct vertical positions, in addition to the interrupt-driven updates. It is therefore a useful diagnostic for the different application/latch behavior of horizontal and vertical scroll, not just a static horizontal offset.

## 4. Comparison with emulator implementations

### 4.1 MAME — Sega 315-5124

Source: [MAME 315_5124.cpp](https://github.com/mamedev/mame/blob/master/src/devices/video/315_5124.cpp)

The current MAME source:
- copies R8 at the line timer;
- allows a write to update the R8 copy only through the configured X-scroll latch boundary (HPos 21 for the 315-5124);
- copies R9 at the beginning of the active display;
- computes the fine-scroll leading-pixel palette selector from `tile_line - 1`, where `tile_line` already includes the low three bits of the active vertical-scroll value.

The last point is the confirmed source-level discrepancy fixed by PR #920.

### 4.2 Ares

Source: [Ares SMS background.cpp](https://raw.githubusercontent.com/ares-emulator/ares/master/ares/ms/vdp/background.cpp)

Ares' `Background::setup()` copies both HScroll and VScroll into its background latch. `graphics3()` then uses those latched values for background coordinate generation. Since setup is part of its scanline pipeline, this is a different R9 update model from MAME's active-display-start capture.

This difference must not be resolved by blindly choosing one emulator. It requires hardware evidence or a test ROM whose expected result is independently established.

### 4.3 Sega Emulator

Source: `native/video_core/src/sms/vdp.rs`

The current model:
- maintains an R8 latch for the following scanline, with the HPos 21 write boundary;
- holds active-display R9 writes as pending and applies them at the completed-visible-frame boundary;
- renders the Mode 4 background using source coordinates derived from R8/R9;
- previously selected the fine-scroll leading-pixel tile-$100 row from `(output_y - 1) & 7`, omitting `R9 & 7`.

The R8/R9 latch model is structurally closer to MAME than to Ares. This is a source-level comparison, not proof of physical hardware accuracy.

## 5. Confirmed renderer discrepancy

MAME derives the tile-$100 selector row from its `tile_line` calculation:

```text
tile_line = output_y - (8 - (R9 & 7))
parse_line = tile_line - 1
parse_row = (output_y + (R9 & 7) - 1) & 7
```

The previous Sega Emulator code used:

```text
parse_row = (output_y - 1) & 7
```

For nonzero fine vertical scroll, this reads a different bitplane row and can choose the wrong background palette for the first 1–7 pixels of a line when R8 has a nonzero fine-scroll component.

PR #920 updates the row calculation and adds a regression test for R8=3, R9=1. The test distinguishes row 0 from row 7 in tile $100.

This is a localized, reproducible mismatch. It does not by itself explain the entire reported visual failure.

## 8. Runtime-path audit — 2026-11-15

This section records a source audit of the current PR head. It does not claim that the ROM has been executed.

### 8.1 Actual runtime path exists

The current runtime path is:

`SmsTemporalWorker → SmsTemporalMachine → SmsTemporalBus → SmsVdp`.

The worker constructs the temporal machine with the selected region and SMS1 `Sega3155124` profile. In `SmsTemporalBus::dispatch_next()`, the scheduler dispatch is consumed, the VDP is advanced by the elapsed Z80 T-states, and only then is the completed bus operation applied. A VDP port write therefore follows the scheduled bus-completion boundary; no GUI or direct-register simulation is required.

Relevant implementation:
- `native/sms_core/src/temporal_bus.rs`: `dispatch_next()` and `write_port()`.
- `native/sms_core/src/temporal_machine.rs`: `step_frame()`, `step_instruction()`, `dispatch_next()`.
- `rust/runtime/sms-runtime/src/worker.rs`: SMS1 hardware-profile construction and worker frame stepping.

### 8.2 Existing trace is insufficient for the requested differential

The current instrumentation already records actual bus completions:
- `SmsTemporalTraceEvent::BusCompleted`: Scheduler timestamp, request ID, operation, address, base T-states, WAIT T-states and data.
- `SmsTemporalPortWrite`: port, value and completion timestamp.

However, neither record currently carries the executing instruction's starting PC or the VDP beam position (frame, scanline, T-state and HPos) at the same event. The debugger snapshot exposes PC and VDP position only when a snapshot is requested; it cannot reconstruct every R8/R9 write's instruction and beam location after the fact.

A non-invasive bus-boundary trace extension is therefore required. It must record the pre-completion instruction PC and the VDP raster/latch snapshot at the existing scheduled dispatch boundary. It must not add instruction callbacks, advance time, or change bus ordering.

### 8.3 Existing in-game smoke test is not a visual differential harness

`rust/runtime/sms-runtime/tests/in_game_rom_smoke.rs` already executes user-supplied ROMs through `SmsTemporalWorker` and a real `FrameMailbox`. Its default campaign is 1,800 frames. It verifies instruction progress, frame dimensions/payload, non-black output and state/frame fingerprints.

It does not currently:
- verify the exact ROM SHA-256 before execution;
- save lossless frame captures;
- select and label frame indices for comparison;
- export every R8/R9 write with PC and beam position;
- compare images or traces against MAME/Ares.

Consequently, a passing smoke test is not evidence that this visual test ROM is correct.

### 8.4 R9 latch model is not yet a proven root cause

The current SMS1 code stores R9 writes made during active display in `pending_scroll_y` and commits the pending value at the visible-area/frame-publication boundary (line 192, T16 in the 192-line profile). MAME's 315-5124 implementation copies R9 at the beginning of active display. Both models make an R9 value written during one active display available to the following active display, rather than changing the current frame's active lines.

This means the mere existence of `pending_scroll_y` does not establish a defect. The Ares scanline-latch model differs, but Ares alone is not a hardware oracle. Any R9 correction must be supported by the exact write sequence and a synchronized output comparison.

### 8.5 Remaining candidate boundaries

The runtime comparison must now distinguish, in this order:
1. VCounter read completion and the exact loop transition at $40/$80.
2. Z80 instruction PC and interrupt service timing for writes originating at $0038/$0068.
3. R8 writes, HPos at bus completion, HPos 21 latch decision and next-line visibility.
4. R9 writes, pending value, active-display latch and next-frame visibility.
5. VDP framebuffer pixels at the same frame/scanline phase.

No Scheduler, Z80, VDP timing or renderer correction is justified by the source audit alone.

## 9. Additional visual symptom report from the project owner — 2026-11-15

The project owner clarified the observed comparison against Ares. This is a user-reported observation, not yet an independently captured or frame-synchronized reproduction.

### 9.1 Reported Ares behavior

The test image contains three visually distinct raster scroll regions, including background content and visually overlapping/overlaid blocks:
- The upper region follows the expected Ares movement.
- Two large overlaid blocks move horizontally from right to left and remain visually distinct instead of collapsing into the surrounding background.
- The lower region scrolls vertically in a regular straight downward direction.

### 9.2 Reported Sega Emulator behavior

- The two large overlaid blocks barely form. Their pixels appear to merge/collide with the background instead of preserving the expected visible separation/overlap.
- The lower region moves in the opposite vertical direction (bottom-to-top) and along a diagonal biased to the left.
- That lower-region trajectory resembles the trajectory of the upper region, even though the upper region itself follows Ares correctly.

### 9.3 Diagnostic implications

This symptom set is broader than the fine-scroll leading-pixel defect fixed by the current PR:
1. The missing/merged blocks require checking background tile fetch/address selection, tile attributes, palette index/transparency handling, and raster-span composition. Do not assume these are hardware sprites; the ROM's SAT initialization analysis indicates the principal moving content is Mode 4 background data.
2. The lower region's reversed vertical direction requires checking the effective Y coordinate and R9 value/sign/wrap for each raster region, including whether the correct R9 write is visible at the intended scanline boundary.
3. The lower region sharing the upper region's leftward diagonal trajectory suggests a possible stale or incorrectly shared scroll state between raster regions. Verify independent R8/R9 state at each boundary rather than assuming a single frame-wide scroll value is sufficient.
4. Because the upper region reportedly tracks Ares, a global inversion of scroll direction or a universal R8 formula defect is not currently the leading explanation. The first divergence is likely region-/boundary-specific, but this remains a hypothesis pending trace and captures.

### 9.4 Important Mode 4 terminology

The analysis must distinguish visually overlaid background sections from actual independent hardware planes or sprites. SMS Mode 4 does not provide multiple independently scrolling background planes like later 16-bit systems. The test's visual regions are produced through raster register changes and background/name-table content. The SAT finding must be retained unless runtime evidence contradicts it.

### 9.5 Updated investigation priority

Before changing the renderer, instrument and compare the three region transitions:
- last scanline of upper region;
- first and subsequent scanlines of the middle/overlaid region;
- first scanline and steady-state of the lower region.

For each transition, capture the CPU's R8/R9 write completion, VCounter read, VDP beam position, effective latched scroll values, name-table row/column, tile pattern row, tile attributes, palette index and final RGB output.

The first divergence must be classified as:
- incorrect CPU/port write timing;
- incorrect register latch/state propagation;
- incorrect background fetch/address calculation;
- incorrect tile/palette composition;
- or frame presentation.

No root cause is established by this symptom report alone. No temporal or composition correction is authorized without synchronized evidence.
